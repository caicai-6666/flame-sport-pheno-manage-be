# 积分与奖品查询业务域

## 1. 功能目标与范围

`rewards` 是查询智能体的独立业务域，用于回答用户、部门、赛季参与、赛季结算积分、全局积分流水、积分商品和奖品履约相关的只读问题。

该业务域复用查询智能体的业务对齐、查询规划、SQL 生成与校验、结果翻译、结果审计、会话交互和 SSE 能力，不复制通用工具或流水线。

当前允许查询的表为：

```text
department
user
season
season_user
product
point_record
```

当前不包含运动项目、运动进度、运动凭证和排行榜表。需要这些数据时，应使用 sports 业务域。

---

## 2. 查询主体与业务规则

查询规划必须先确定查询主体，并在 `query_goal` 和 `row_granularity` 中表达一行代表的对象。

| 用户目标 | 查询主体 | 默认数据口径 |
| --- | --- | --- |
| 查看当前有多少积分 | 用户当前可用积分 | 取用户最新有效积分流水的余额事实，不累加历史余额 |
| 查看积分明细 | 积分变动流水 | 一行代表一条积分变动记录 |
| 查看赛季获得多少积分 | 用户赛季结算记录 | 使用赛季参与记录中的最终积分 |
| 查看积分是否已经发放 | 用户赛季结算记录 | 使用赛季结算积分的发放状态 |
| 查看兑换记录 | 商品兑换履约记录 | 一行代表一条商品兑换积分流水 |
| 查看待发放奖品 | 商品兑换履约记录 | 必须限定有效商品兑换和待发放履约状态 |
| 查看可兑换商品 | 商品目录 | 一行代表一个商品，不使用兑换履约状态 |

查询逐条积分或兑换记录时，记录 ID 是定位主体的辅助字段，不能替代用户要求的业务字段。用户明确只要求 ID 时，才允许生成 ID-only 查询。

逐条结果必须返回与查询主体一致的主键：

| 查询主体 | 必须返回的主键 |
| --- | --- |
| 积分流水、兑换记录或奖品履约记录 | `point_record.id` |
| 用户赛季结算记录 | `season_user.id` |
| 商品目录 | `product.id` |

关联表的主键不能代替主体主键。例如，一条待发放奖品结果只返回 `product.id`，仍然无法唯一定位对应的兑换流水。

规划层中的返回字段用途只作为简短表头标签，例如“积分流水 ID”“当前积分”“商品名称”。查询口径、最新记录判断、前端定位用途等说明必须放在查询目标、筛选条件或业务口径中，不能混入表头。

## 3. 关键状态与条件

### 3.1 赛季积分

`season_user.final_points` 的含义为：

```text
NULL = 尚未结算
0    = 已结算但没有获得积分
> 0  = 已结算并得到积分
```

`season_user.points_issued` 表示该赛季积分是否已经写入用户全局积分流水：

```text
0 = 未发放
1 = 已发放
```

### 3.2 当前余额

`point_record.points_after` 是某条积分变动完成后的全局余额。查询当前余额时，必须取用户最新有效流水的 `points_after`，不能把多条历史余额相加。

“最新有效流水”采用稳定的全序判定：

1. 当前流水必须有效。
2. 同一用户不存在另一条有效流水，其 `created_at` 晚于当前流水。
3. `created_at` 相同时，不存在 `id` 大于当前流水的有效流水。

规划层使用两个 `point_record` 角色和 `none` 量词表达该口径。候选更晚流水的有效状态放在成员条件中；同一用户关联、时间比较和同时间主键比较放在 `correlation_condition` 中。SQL 层只负责严格实现已经通过领域校验的正式计划。

### 3.3 商品履约

查询待发放奖品时，必须同时满足：

```text
change_type = 'exchange'
product_id IS NOT NULL
status = 1
gift_distribution_status = 'pending'
```

`gift_distribution_status` 只对有效商品兑换流水有业务意义。赛季奖励、兑换退款和人工调整不应被解释为待发放奖品。

四项条件必须作用于同一个查询块中的同一个积分流水角色，并通过 `AND` 同时成立。不同查询块或不同别名上的条件不能拼接成待发放口径，条件位于 `OR` 分支时也不视为必然成立。

### 3.4 赛季范围与正式参与

“本赛季”和“当前赛季”只指进行中的赛季，不包含结算中、已结束或仅按日期推测的最近赛季。

查询正式参与或正式报名用户时，必须同时满足：

```text
season_user.status = season.required_project_count
season_user.level_id IS NOT NULL
```

只有用户明确要求查看报名中、未完成报名或全部参与记录时，才允许放宽该口径。

## 4. 赛季与全局流水边界

`season_user` 记录用户在具体赛季中的结算结果，`point_record` 记录用户跨赛季共享的全局积分变动。

当前 `point_record` 没有结构化 `season_id`，因此：

- 可以查询某赛季的最终积分和发放状态；
- 可以查询用户全局积分流水；
- 不能仅凭 `change_type = season_reward` 将某条全局流水可靠归属于指定赛季。

如果未来需要严格查询“某赛季实际写入的积分流水”，需要补充结构化赛季关联或独立的奖励来源模型。

## 5. 实体解析

以下实体允许使用名称检索：

| 实体 | 表 | 匹配方式 |
| --- | --- | --- |
| 用户 | user | 精确匹配失败后有限预算模糊匹配，并在相似候选出现时询问用户 |
| 部门 | department | 精确匹配失败后有限预算模糊匹配 |
| 赛季 | season | 精确匹配 |
| 商品 | product | 精确匹配失败后有限预算模糊匹配 |

用户名称和商品名称都不能作为唯一身份。名称未精确命中时，不得猜测筛选值；需要通过实体检索和用户确认得到稳定 ID。

“积分”没有上下文时，业务对齐层需要区分当前余额、积分流水、赛季结算积分和兑换相关积分。“奖品”没有上下文时，需要区分商品目录、兑换记录和履约状态。无法唯一判断时必须询问用户，不能由模型自行选择查询主体。

## 6. 计划校验

积分与奖品业务域的计划校验器负责阻止以下错误：

- 当前余额查询没有返回余额字段，或没有稳定排除同一用户的更晚有效流水；
- 赛季结算查询没有返回最终积分或发放状态；
- 兑换或奖品履约查询没有使用积分流水；
- 使用奖品履约状态却没有限定商品兑换类型；
- 待发放奖品没有在同一流水角色上同时限定兑换类型、商品非空、流水有效和待发放状态；
- 查询商品目录却混入兑换履约状态；
- 逐条结果没有返回与真实查询主体一致的 ID；
- 对齐结果只说“积分”或“奖品”，没有明确具体业务口径。

校验失败会作为原终止工具的结构化失败结果返回模型，指出错误字段、错误原因和唯一修复动作。

## 8. 验证方式与限制

自动化测试覆盖：

- `rewards` Profile 资源加载和表白名单；
- 积分域 Prompt 不混入运动凭证语义；
- 模糊“积分”需求被要求进一步澄清；
- 模糊“奖品”需求被要求进一步澄清；
- 当前余额字段及同时间主键决胜的最新有效流水校验；
- 待发放奖品四项条件的同块、同角色约束；
- 赛季结算、商品目录和兑换记录的主体 ID 约束。

当前实现只提供只读查询，不执行积分发放、商品发放、退款或其他写操作。查询状态和事件仍受查询智能体进程内会话保留策略约束。
