# 赛季结算应用编排

> **文档目的**
>
> 本文档说明管理端如何把赛季状态转换、客户端立即初审、补传资格、终审和最终定分编排为可恢复流程。

## 1. 用例目标

结算编排由进程内定时任务触发，负责把到期赛季推进到结算中，并持续处理因停机、网络失败、待终审或补传资格而尚未收敛的结算赛季。

业务规则以[赛季结算规则](../domain/season-settlement.md)为准，本应用服务只负责调用顺序、事务和失败恢复。

管理端可通过[赛季结算 API](../api/settlement.md)只读获取唯一结算中赛季、正式参赛记录主键列表和全部待终审凭证。查询不会触发本任务的任何状态变化。

管理员确认不再等待终审和补传时，可以调用一键结算接口强制收口唯一结算中赛季。环境开关启用后，定时任务也会在赛季结束日加配置天数后的首次轮询复用同一服务。该路径不会调用外部初审服务，而是统一拒绝所有待初审和待终审凭证，再依据终审通过凭证重算进度、清空补传资格表、定分、发放积分并结束赛季。

---

## 2. 执行阶段

每轮任务依次执行：

1. 锁定当前结算中赛季；存在时不推进另一个赛季。
2. 锁定唯一到期的进行中赛季，将其更新为结算中，并在同一事务清空上一周期资格表。
3. 查询当前结算中赛季截止前仍为 `pending` 的正式参赛凭证。
4. 在数据库事务外分批并发调用客户端后端立即初审接口。
5. 只要仍有遗留 `pending`，结束本轮且不处理任何用户定分。
6. 查询资格状态为 `2` 的已补交记录，在数据库事务外分批并发调用客户端补交专用初审接口。
7. 只要仍有待补交初审记录，结束本轮且不处理任何用户定分。
8. 按主键游标分页读取未定分用户，每个用户使用独立事务处理；先自动拒绝已经由终审通过记录独立撑满项目的额外待终审凭证，再为剩余凭证登记资格并同步固化刚完成初审时使用的项目合格指标，或在无待审记录时直接定分。
9. 等待管理员逐个发放已经定分的赛季积分。
10. 尝试把没有未定分、未发放用户和非零资格状态的赛季推进为已结束。

一键结算使用独立的同步编排：先稳定锁定赛季全部相关用户和参与记录，再逐用户关闭未审核凭证、重算进度、补齐定分和积分流水，随后整表清空补传资格，最后更新赛季状态。该路径的任何用户失败都会回滚整个赛季操作，不采用常规轮询的单用户失败隔离策略。

外部初审和数据库写事务不会重叠。客户端后端已负责凭证版本条件写回，管理端以重新查询数据库作为调用结果的最终事实。

---

## 3. 事务边界

| 阶段 | 事务范围 |
| --- | --- |
| 赛季初始化 | 锁定赛季、`1 → 2`、清空资格表 |
| 遗留初审查询 | 短只读事务 |
| 客户端立即初审 | 无管理端数据库事务 |
| 客户端补交初审 | 无管理端数据库事务；结果与资格状态由客户端原子写回 |
| 单用户结算 | 锁定 `season_user`、拒绝与进度调整、资格写入、定分、通知 |
| 管理员结算终审 | 复用终审核心，锁定用户与项目，原子处理进度回退与回补、资格状态、可能的定分和通知 |
| 积分发放 | 用户主记录锁、参赛记录锁、最新积分流水锁、奖励流水和发放标记 |
| 赛季结束 | 带完整性条件的单条状态更新 |
| 一键结算 | 凭证拒绝、进度重算、资格表清空、定分、通知、积分流水、发放标记和赛季结束共享一个事务 |

零完成用户的所有待终审记录在一个用户事务内收口。额外凭证的拒绝、项目进度回补、资格关闭和汇总提示也处于同一用户事务。某个用户数据异常只回滚该用户，不影响已经提交的其他用户；任务记录用户和赛季 ID 后继续处理。

---

## 4. 并发与幂等

- 状态初始化先锁定结算中和到期赛季，多实例不能重复清空资格表。
- 资格依靠 `proof_record_id` 唯一键执行幂等更新；首次插入固化规则快照，重复开放只允许 `0 → 1`，不得覆盖状态 `2`、`3` 或已有快照。
- 额外凭证只在终审通过记录的原始贡献已经独立达到项目目标时自动拒绝，拒绝后的回补仍优先使用终审通过记录。
- 定分先锁定 `season_user`，并以 `final_points IS NULL` 作为最终条件。
- 定分和结算通知处于同一事务，重复任务不会生成第二条通知。
- 积分发放按用户级锁顺序计算最新余额，流水写入和 `points_issued` 条件更新处于同一事务。
- 终审先取得结算用户行锁，再按项目进度、凭证顺序获取锁，与任务使用相同顺序。
- 赛季结束更新同时检查未定分用户、积分未发放用户和有效资格，重复执行保持幂等。
- 一键结算先按用户 ID 加锁，再锁定赛季和参与记录；锁定后重新核对人员集合，防止并发报名纠错、终审或发放越过事务边界。
- 一键结算成功后赛季已经离开结算状态，重复请求不会再次创建积分流水；并发请求只有一个能够提交。

---

## 5. 外部失败

客户端后端的非成功响应、连接错误或响应契约错误不会转换为审核拒绝。当前轮停止继续拉取新批次，保留数据库中的 `pending`，由后续轮询重新尝试。该规则同时适用于赛季遗留立即初审和补交专用初审。

单条 `409` 可能表示其他任务已经处理或用户在模型调用期间重传；管理端不解析未知响应正文，而是重新统计数据库中的待初审数量。

---

## 6. 通知

定分成功时只写入 `season_user.final_points`，`points_issued` 继续保持为 `0`。结算通知标题为 `赛季结算结果`，包括赛季、完成项目数和最终积分。零完成通知说明不开放赛后补传；仅当前赛季全部项目确定达标时计算连续奖励，存在奖励时额外展示挑战积分和连续奖励。

管理员随后通过[赛季结算 API](../api/settlement.md)发放积分。发放流程按项目完成档位复核 `final_points`，在流水提示中分别标明保底积分、挑战积分和连续完成额外奖励，再更新 `points_issued`，不重复创建钉钉通知。

自动拒绝额外待终审凭证时，同一批只写入一条标题为 `赛季凭证处理提示` 的通知，说明赛季、关闭数量和无需继续终审的原因。

管理端只写入通知表，钉钉投递仍由客户端后端负责。通知失败会回滚当前用户的定分和相关审核调整。

一键结算中，自动拒绝汇总通知、首次定分通知和积分流水与赛季结束共享一个事务。任一通知写入失败会回滚本次整个赛季收口；钉钉后续投递失败不会反向撤销已经提交的结算数据。
