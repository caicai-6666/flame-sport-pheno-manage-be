# 应用服务层设计

> **文档目的**
>
> 本文档定义 `app/services/` 的职责、调用方向、事务边界和异常处理规则，供后续管理端用例按统一分层扩展。

## 1. 设计目标

应用服务层负责把一个管理端用例需要的业务步骤、仓储访问和外部服务调用编排在一起，使 HTTP 路由不直接承载业务判断或事务管理。

当前调用方向固定为：

```text
管理前端请求
    │
    ▼
router：路径参数位置、认证依赖、服务调用、状态码映射
    │
    ├── schemas：请求校验、响应结构、纯传输格式适配
    │
    ▼
services：用例规则、事务边界、调用编排、稳定应用异常
    │
    ├── repositories：参数化 SQL、查询结果映射
    ├── clients：客户端后端等外部系统适配
    └── core：配置、令牌缓存等应用基础能力
```

> **核心约束**
>
> 路由不得越过服务层直接调用仓储或内部 HTTP 客户端；Schema 不得依赖路由、服务或仓储；仓储与客户端也不得依赖 FastAPI 的请求、响应或 `HTTPException`。

| 服务模块 | 当前用例 | 主要依赖 | 关键职责 |
| --- | --- | --- | --- |

| `app/services/agent_queries.py` | 创建、查询、恢复、取消智能体查询并读取结果 | `AgentQueryManager` | 将进程内会话和完整流水线结果转换为不含 SQL、模型原文与技术轨迹的安全 HTTP 数据 |
| `app/services/season_statistics.py` | 查询当前赛季统计与指定用户项目进度 | 赛季统计仓储 | 管理只读事务，确保当前赛季唯一，查询有效参赛项目，将仓储一致性异常转换为应用异常 |
| `app/services/seasons.py` | 查询与创建赛季 | 赛季仓储、项目仓储 | 映射赛季状态含义；校验完整日历月、历史边界和项目容量并创建未开始赛季 |
| `app/services/season_settlements.py` | 查询、初始化并持续收敛赛季结算 | 结算仓储、积分仓储、凭证服务、通知仓储、客户端后端 | 在只读事务返回唯一结算赛季、正式参赛记录、批量用户详情及待终审队列；推进到期状态并清空资格；补齐遗留初审；分用户登记资格、定分；按用户级锁写入赛季奖励流水并标记发放；结束已完全收敛的赛季 |
| `app/services/users.py` | 批量查询用户基础信息 | 用户仓储 | 用户 ID 保序去重，管理只读事务，编排批量查询 |
| `app/services/suggestions.py` | 查询、处理用户意见 | 意见仓储 | 只查询可见且待处理的意见；在行锁保护下将意见标记为拒绝或已解决，并保证重复动作幂等 |
| `app/services/projects.py` | 查询与创建项目、查询项目等级规则、修改项目可见状态 | 项目仓储、配置窗口守卫、客户端后端 | 管理查询和写事务；创建时校验 WebP 与完整规则矩阵，原子写入项目配置，并通过固定上游接口保存唯一地址图标；状态修改在窗口与项目行锁保护下完成 |
| `app/services/configuration_guard.py` | 校验激活赛季配置变更窗口 | 激活赛季锁定仓储、环境配置 | 统一识别当前激活赛季、计算配置截止时刻，并拒绝超时或多激活赛季下的高影响写入 |
| `app/services/project_levels.py` | 查询、创建挑战等级，修改奖励积分与项目规则配置 | 挑战等级仓储、项目规则仓储、配置窗口守卫 | 管理查询和写事务；原子创建等级及空值规则，在窗口与行锁保护下覆盖奖励积分或局部修改既有规则指标值，并映射业务冲突 |
| `app/services/products.py` | 新增与查询商品、修改商品基础资料与可见状态、查询兑换礼品与奖品信息，处理发放审核 | 商品仓储、通知仓储、配置窗口服务、客户端图片服务 | 管理查询和写事务；新增奖品默认上架，数据库提交后落盘 WebP；基础资料局部更新在提交后上传新图和清理旧图；既有奖品积分修改受配置窗口保护；上下架在商品行锁下幂等更新；发放审核首次进入终态时原子创建结果通知，拒绝时同时锁定用户最新积分流水并新增退款流水 |
| `app/services/proofs.py` | 查询待终审凭证、记录终审 | 凭证仓储、通知仓储、结算服务 | 管理查询与终审事务；拒绝时撤销贡献并回补项目进度；结算中同步补传资格并在最后一条终审通过后立即尝试定分 |
| `app/services/images.py` | 中转头像、项目图标、商品图片与运动凭证图片，上传新项目图标与商品图片 | 客户端后端适配器 | 按预定义资源固定上游路径、隔离网络与状态异常、校验图片媒体类型、附带缓存时效；按固定 multipart 协议上传 WebP 项目图标，并向 `/product/replace` 上传 WebP 奖品图片和替换地址 |

`app/services/__init__.py` 只声明包，不集中重新导出所有服务，避免形成隐式公共 API 和循环依赖。

健康检查只返回进程存活信息，不包含业务用例，因此仍由路由直接构造响应。`require_admin_token` 是所有受保护路由共享的 HTTP 认证依赖，也不迁入具体业务服务。

查询智能体不使用请求级 `AsyncSession`。服务调用进程级查询管理器；业务对齐模型通过异步客户端执行，尚未异步化的子图在线程桥接中运行，受限 SQL 使用独立只读数据库事务。详细编排见 [查询智能体应用编排](query-agent.md)。

## 3. 分层边界

### 3.1 Schema 层

`app/schemas/` 只负责：

- 定义 Pydantic 请求体与响应体；
- 定义 Query 或 Body 会复用的约束类型；
- 校验字段类型、长度、枚举、空补丁和字段间结构关系；
- 为 multipart 中的 JSON 字符串提供无副作用的强类型适配器。

Schema 不查询数据库、不读取运行配置、不调用服务，也不抛出 `HTTPException`。需要判断赛季配置窗口、资源是否存在、状态是否允许流转或图片是否被共享时，必须由服务层处理。Schema 模块只能依赖标准库、Pydantic 等传输层基础类型，禁止反向导入 `app/router`、`app/services` 或 `app/repositories`。

### 3.2 路由层

`app/router/` 只负责：

- 声明路径、HTTP 方法和 Query/Body 参数位置；
- 引用 `app/schemas/` 中对应的请求与响应模型；
- 注入数据库会话、客户端适配器和认证依赖；
- 调用一个职责明确的应用服务；
- 将服务结果序列化为响应；
- 将稳定的应用异常映射为 HTTP 状态码和安全提示。

路由不定义 Pydantic `BaseModel`，也不应自行开启数据库事务、执行 SQL、进行跨数据源编排或解析上游业务错误正文。

### 3.3 服务层

`app/services/` 负责：

- 执行与传输协议无关的用例规则；
- 确定仓储及外部客户端的调用顺序；
- 管理属于整个用例的事务边界；
- 把下层实现异常转换为稳定的应用异常；
- 返回不可变或语义明确的结果对象。

服务层不得构造 `Response`、抛出 `HTTPException` 或读取请求头。服务函数接收已经由路由校验过的参数和注入依赖，使其可以脱离 ASGI 环境单独测试。

### 3.4 仓储与客户端层

`app/repositories/` 只负责数据库访问、参数绑定和结果映射，不自行创建、提交或关闭会话。`app/clients/` 只封装外部协议、基础地址、连接池和通用状态检查。

仓储返回“未找到”、数据结果或仓储一致性异常；客户端返回上游响应或协议异常。如何组合这些结果并形成管理端用例语义，由服务层决定。

## 4. 事务与失败处理

数据库会话由 FastAPI 请求依赖创建并传给服务，服务使用同一个 `AsyncSession` 开启用例事务：

```python
async with session.begin():
    result = await repository_operation(session)
```

事务规则如下：

1. 只读数据库用例也由服务显式声明事务边界，便于后续组合多个一致性查询。
2. 写用例应把必须原子完成的多表变化放入同一个服务事务。
3. 仓储不得调用 `commit()`、`rollback()` 或关闭注入的会话。
4. 服务可以按明确业务阶段提交，但必须保证积分、进度、审核等不变量不会暴露部分完成状态。
5. 外部 HTTP、模型或文件调用不应长时间占用数据库事务；需要组合时应先确定可重试和补偿语义。

项目规则配置修改属于高影响写用例。服务必须先执行统一赛季配置窗口校验，再锁定 `(project_id, level_id)` 规则；请求中的 `label` 只用于定位既有指标，服务仅替换 `value`，并在同一事务中保存指标、挑战副描述与规则备注，禁止由路由直接拼接或覆盖 JSON。

项目可见状态修改同样属于高影响写用例。服务先执行统一赛季配置窗口校验，再锁定 `project.id` 并覆盖 `status`；隐藏只改变客户端可见口径，不删除项目及历史关联，重复提交相同状态保持成功。

项目创建需要同时维护数据库配置和客户端后端文件。服务先在事务外校验 WebP，随后在同一数据库事务内依次校验配置窗口、共享锁定全部等级、验证完整规则矩阵、批量写入项目及子配置，并调用有超时限制的固定图标上传接口。图标上传失败会使数据库事务回滚；上传成功而数据库最终提交失败时可能遗留唯一地址的孤立文件，当前没有删除接口可执行自动补偿。该事务会短暂等待一次内部 HTTP 调用，这是在现有上游契约下保证“不保存无图标项目”的明确取舍。

商品可见状态修改在单一事务中锁定 `product.id` 并覆盖 `status`，不删除商品或改写历史兑换关联。重复提交相同状态保持成功。当前配置时间窗口只明确约束奖品积分值修改，商品上下架不执行该窗口校验。

奖品新增先在事务外校验真实 WebP 并生成唯一地址，再在单一事务内写入默认上架的商品记录。数据库事务提交后，服务以 `old_image_url = null` 复用客户端 `/product/replace` 落盘图片。新增奖品当前不执行配置窗口校验；客户端失败会形成商品已创建但图片未落盘的部分成功状态，路由必须返回明确的 `502` 提示。

商品基础资料更新先在事务外限量读取并校验可选图片，声明媒体类型和真实格式都必须是 WebP；有效图片会获得不复用的 `.webp` 地址。服务随后在单一数据库事务内锁定商品并应用显式补丁。只有补丁包含 `points_required` 时才执行激活赛季配置窗口校验；名称、描述和图片可独立修改。图片变更时，数据库事务先提交，再检查旧地址是否仍被其他商品引用，最后通过 multipart 调用客户端 `/product/replace` 上传新图并按需清理旧图。该顺序避免数据库失败后旧文件已被删除，但客户端失败会形成数据库已提交而新图未写入的部分成功结果，必须向路由传播而不能伪装回滚。

业务结果通知使用事务内通知记录实现可靠交接。凭证只在普通终审拒绝时创建通知；赛季定分创建一条汇总通知；礼品只在首次进入 `distributed` 或 `rejected` 时创建通知。通知初始状态为 `pending`，与对应审核状态、资格、定分、进度调整或积分退款一起提交；通知写入失败会使当前业务事务整体回滚。管理端后端不在事务中调用钉钉接口。

赛季结算任务由 `app/jobs/season_status.py` 触发。状态转换和资格表清空使用同一事务；遗留初审在事务外调用客户端后端；每个用户以独立事务锁定 `season_user` 并处理审核、进度、资格、定分和通知。任务按主键游标分批读取，单个用户失败不会扩大到其他已提交用户。

服务异常不包含 SQL、连接地址或未知上游响应正文。路由只根据异常类型选择状态码，不能依赖解析异常字符串判断业务分支。

## 5. 扩展规则

新增管理接口时，应按以下顺序确定实现位置：

1. 在对应 `app/schemas/<业务>.py` 定义请求、响应及字段级校验。
2. 在路由声明路径、参数位置、认证要求和异常映射。
3. 在同一业务主题的服务模块新增用例函数；只有职责明显独立时才新增服务文件。
4. 将数据库查询放入对应仓储，将内部 HTTP 调用放入客户端适配器。
5. 在服务中组合依赖、事务和应用异常。
6. 分别测试 Schema 边界、服务用例和 HTTP 可观察行为。

不要为每个简单函数创建类或接口。只有出现多种可替换实现、复杂状态或明确测试替换点时，才引入策略、协议或工厂抽象。

## 6. 安全与并发

- 服务只接收固定依赖，不允许请求参数决定数据库连接或客户端后端基础地址。
- 图片服务只允许固定请求客户端后端 `/avator`、`/project_icon`、`/product` 与带正整数 ID 的 `/proof_record/{id}`；项目图标上传只允许固定的 `POST /project_icon`，奖品 WebP 上传替换只允许固定的 `POST /product/replace`，不能退化为任意 URL 代理。
- 认证服务不返回管理员密钥或缓存内部摘要。
- 数据库写用例必须评估重复请求和并发更新；仅依赖应用层先查后写不能替代数据库约束或锁。
- 服务日志不得记录完整令牌、管理员密钥、数据库密码或无脱敏个人信息。

## 7. 验证方式

在仓库根目录执行服务层测试：

```bash
python -m unittest tests.test_services tests.test_project_status tests.test_project_creation tests.test_season_settlement -v
```

测试覆盖：

- 管理员令牌签发结果和无效密钥异常；
- 项目、用户和当前赛季查询的事务进入与退出；
- 用户 ID 保序去重后再调用仓储；
- 当前赛季不存在和多激活赛季的应用异常转换。
- 赛季创建的完整日历月、历史结束边界、可见项目容量、默认状态和事务回滚。
- 项目可见状态修改的配置窗口、项目行锁、事务回滚、重复写入和不存在分支。
- 项目创建的 WebP 约束、完整等级覆盖、指标标签一致性、批量写入、客户端上传契约和失败回滚。
- 商品资料局部更新、WebP 真格式校验、唯一图片地址、数据库先提交顺序、multipart 上游协议和共享旧图保护。

服务层测试使用会话和依赖替身，不访问开发数据库或真实客户端后端。各 API 的状态码、认证和序列化行为继续由对应路由测试覆盖。
