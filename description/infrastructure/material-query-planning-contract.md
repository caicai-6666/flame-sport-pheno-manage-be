# 纯文本原料查询规划契约

## 1. 目标与范围

查询规划子图通过 `query_material_data`、`shape_material_data` 和 `submit_final_query_result` 形成“查询、观察、塑形、观察、选择”的闭环。规划模型不生成 SQL，也不直接处理完整结果；它只提供纯文本指导、观察受限预览，并选择一份已经验证的塑形结果交给后续翻译层。

旧 `submit_material_query_plan` 和 `execute_natural_language_query` 不再作为生产规划终止协议。SQL 查询与原料塑形仍由各自独立子图完成，但由 Planning 通过工具调用，不再由主 Pipeline 在规划结束后分别发起。

---

## 2. 工具契约

三个核心工具的职责如下：

| 工具 | 主要参数 | 成功结果 | 失败语义 |
| --- | --- | --- | --- |
| `query_material_data` | `guidance`、`required_tables` | `material_result_id`、完整行数、真实表头和前 `5` 行 Markdown 预览 | 返回友好原因与修正方向，不产生结果 ID |
| `shape_material_data` | `material_result_id`、塑形指导 | `shaped_result_id`、来源原料 ID、完整行数、真实表头和前 `5` 行 Markdown 预览 | 返回友好原因与修正方向，不产生结果 ID |
| `submit_final_query_result` | `shaped_result_id`、选择理由 | 发起最终表格复核；操作员确认后将完整塑形结果标记为 Planning 最终产出 | 拒绝不存在、失败或不属于本轮的结果 ID；修正意见返回模型继续迭代 |

工具参数由 Pydantic 生成 Function Calling Schema，并在本地再次校验。额外字段、缺少字段和错误类型均被拒绝；兼容层只在首次校验失败后尝试还原嵌套 JSON 字符串，不放宽字段约束。

规划工具循环要求首轮使用一次 `think`。`think.reason` 允许最多 `350` 个字符，应说明已确认事实、仍需判断的问题和倾向的下一步动作。存在会改变动作的新判断点时允许连续调用 `think`，但每轮必须推进判断，不得重复已有结论。连续两次成功思考后，下一轮会临时收到一条 `system_guidance`，提醒模型判断应继续聚焦新问题还是采取读取事实、询问用户、查询原料、塑形、提交最终结果或放弃查询等实际动作；该指导只对紧邻请求可见，任一合法的非 `think` 动作会重置连续计数。

## 3. 查询与塑形职责边界

`query_material_data.guidance` 必须用 Markdown bullet 完整表达数据库筛选、主体资格、排序或数量要求和必取原料。跨明细集合的全部、任一、没有或数量条件必须说明主体资格策略，不能把判断推迟给塑形或前端。

`required_tables` 必须覆盖每个筛选、关联、返回业务值、稳定分组值、动态列值和排序值。关联表中的外键只提供标识，不能代替实体表中的名称等属性。

塑形指导只改变查询成功后的行列布局，不得新增筛选、聚合资格、事实计算或业务值。横向展开必须同时说明一行原料代表的成员和一行最终结果代表的主体，并要求原料中存在稳定主体标识、成员值和排序值。

塑形指导必须恰好包含一条动态列数量声明：普通逐行结果写 `- 动态列数量：不适用`；用户未限定列数的动态展开写 `- 动态列数量：由完整结果决定`；固定数量的目标表头写 `- 动态列数量：固定 N 列`。用户明确列出固定表头时必须使用固定数量，使零行结果仍能构造完整表头。

规划器未读取真实表结构时只使用业务原料名称和来源表，不猜测字段原名。字段到 SQL 的映射由拥有真实表结构的 SQL 子图完成。

---

## 4. 结果 ID 与后台缓存

每次成功的原料查询都获得一个只在本轮 Planning 有效的 `material_result_id`。后台以该 ID 保存完整 `SqlQuerySubgraphResult` 及本次查询指导；规划模型只接收结果 ID、完整行数、真实表头和前 `5` 行预览。

每次成功塑形都获得一个只在本轮 Planning 有效的 `shaped_result_id`。后台保存完整塑形结果、来源 `material_result_id` 和本次塑形指导；规划模型同样只接收两个结果 ID、完整行数、真实表头和前 `5` 行预览。工具明确返回的行数可以判断空结果和结果规模；前 `5` 行只是观察样本，不能用于推断未展示内容、类别分布或极值。

缓存不跨查询会话共享。失败调用不写入缓存，也不产生可引用 ID。`shape_material_data` 只能读取本轮成功的原料 ID，`submit_final_query_result` 只能选择本轮成功且实际观察过的塑形 ID。

Planning 成功结束时，只把最终选中的原料查询结果、塑形结果、两段指导和选择理由组成终态交付；未选中的候选结果随本轮规划上下文释放。完整结果不会写入模型消息、SSE 事件或友好轨迹。

---

## 5. 失败反馈与迭代

两个数据处理工具的失败都是有效观察。工具必须返回友好的失败原因和明确修正方向；Planning 保留上一轮正确内容，只修正查询指导、所需表、结果引用或塑形指导中有问题的部分，然后用更详细、更精确的参数重新调用。

查询失败后不能调用塑形。塑形失败时，如果原料完整，应基于同一个 `material_result_id` 修正布局；如果反馈指出缺少业务值、稳定分组键或排序值，则应重新查询原料。只有反馈揭示真实业务歧义时才询问用户，不能把工具内部错误转嫁给用户。

---

## 6. 业务域注入

提示词通过 `QueryDomainProfile` 注入业务域名称、只读查询范围、核心玩法规则和按依赖顺序排列的表概述。它不读取旧的结构化 `planning_prompt_instructions`，避免把 `query_blocks` 或 `result_shape_plan` 带入当前工具上下文。通用提示词不得引用某个业务域专属的表名或字段示例。

相关事实来源包括：

- 各业务域 `business-context/core-game-rules.txt`
- 各业务域 `table-context/*.txt`

## 7. Pipeline 交付与验证

`submit_final_query_result` 引用校验通过后，系统向操作员展示最终行数和表头；确认后查询规划结果携带最终选中的 SQL 原始结果、塑形结果及其来源信息。主 Pipeline 不再重新执行 SQL 或塑形，而是直接把选中结果交给字段翻译、程序统计和结果审计。操作员提出修正时，Planning 继续原工具上下文，不会交付当前候选。

自动测试应覆盖三个工具的 Schema、查询与塑形成功结果 ID、失败不产生 ID、未知或跨轮 ID 被拒绝、零行结果保留表头、预览最多 `5` 行、多次查询或塑形后只提交选中结果，以及 Pipeline 从 Planning 直接进入翻译。实验入口复用生产工具和提示词完成受控只读验证，避免实验与生产定义漂移。
